# AI Planner — Specification

This is the **canonical specification** for TravelBook's AI Trip Builder. Every rule here is load-bearing: the planner has to behave exactly as described for the Travel Pass metaphor to work.

> Referenced by: [`PROJECT.md`](../PROJECT.md), [`CLAUDE.md`](../CLAUDE.md), [`docs/UI_COMPONENT_LIBRARY.md`](UI_COMPONENT_LIBRARY.md).

## 1. What the AI must produce — the complete itinerary

When a user runs the AI Trip Builder, the output is a **full, time-sequenced itinerary**. It must cover **every** time-sensitive piece of the trip, in chronological order. Nothing is optional in the default output — the user can remove what they don't want afterwards.

### The 12 card slots (in chronological order)

| # | Card | Required? | When |
|---|---|---|---|
| 1 | **Visa** | Always (if destination requires) | Before departure (deadline-aware — must process in time) |
| 2 | **Travel insurance** | Always | Covers entire trip window |
| 3 | **Outbound flight** | Always | Trip start |
| 4 | **Arrival airport → hotel transfer** | Always | Immediately after outbound flight lands |
| 5 | **Hotel(s)** | Always | Covers every night of the trip |
| 6 | **Inter-city / inter-destination transport** | When trip hits > 1 destination | Between destinations (train, intercity bus, domestic flight, ferry) |
| 7 | **Local transport** (day passes, rideshare credits) | Optional, destination-dependent | During the trip |
| 8 | **Activities** | Multiple — matched to purpose + interests | Throughout trip, morning/afternoon slots |
| 9 | **Dining** | Multiple — default yes, user cancels if unwanted | Lunch + dinner slots, especially reservation-requiring restaurants |
| 10 | **Events / entertainment** | If relevant to destination/dates/interests | Specific time slots |
| 11 | **Hotel → departure airport transfer** | Always | Before return flight |
| 12 | **Return flight** | Always (one-way trips are an edge case, not default) | Trip end |

**All of these are generated by default.** The user culls what they don't want by pressing × on the card (which triggers a cascade reflow — see §4).

### Distribution logic

- **Hotels:** if the trip spans multiple destinations, generate one hotel card per destination, with correct check-in/check-out dates.
- **Activities:** density based on trip length and travel style. Rule of thumb: ~1 activity per full day for Comfort, ~2 for Adventure-heavy, ~0.5 for Wellness (more rest).
- **Dining:** at least one dinner per day when a reservation-heavy restaurant is suggested; otherwise one "curated pick" card per destination.
- **Transfers:** airport transfer cards auto-follow the corresponding flight card. If the flight is swapped (different time) or removed, the transfer adjusts or disappears.

## 2. Purpose signal — three inputs, all used together

The AI combines **three signals** to decide what to plan:

1. **Interests tags** (existing) — Beach, Adventure, Culture, Food, Wellness, City, Nature, Sports, Nightlife.
2. **Travel style** (existing) — Budget / Comfort / Luxury.
3. **Trip purpose** (new, explicit) — Leisure / Business / Honeymoon / Family / Wellness / Bachelor(ette) / Adventure / Culture / Celebration / Other.
4. **Free-text description** (new) — optional natural-language field. "5-day anniversary trip, love seafood and quiet beaches, want one big splurge dinner" — the LLM parses this alongside the structured fields.

All four are passed into the LLM prompt. Free-text overrides / refines structured choices when they conflict (e.g. user picks "Budget" + writes "splurge on the final dinner" → dining card for the last night is luxury, everything else is budget).

### Planner form — updated fields

| Field | Type | Required? |
|---|---|---|
| Destination | text | ✅ |
| Start date | date | ✅ |
| End date | date | ✅ |
| Number of travelers | number | ✅ |
| Budget | number + currency | ✅ |
| Travel style | Budget / Comfort / Luxury | ✅ |
| **Trip purpose** | single-select pill (10 options) | ✅ NEW |
| Interests | multi-select pills | Optional |
| **"Tell me about this trip"** | multi-line text | Optional NEW |

Purpose sits directly below Travel Style in the form. Free-text is the last field before "Generate My Itinerary."

## 3. UX — swipe-as-deck, not alt-chip carousel

### The old pattern (REMOVE)

```
┌─────────────────────────┐
│   Main card (selected)  │
│   Flight · $920         │
└─────────────────────────┘
  ┌──────┐ ┌──────┐ ┌──────┐
  │alt #1│ │alt #2│ │alt #3│   ← small chip row — KILL THIS
  └──────┘ └──────┘ └──────┘
```

### The new pattern (BUILD THIS)

```
┌─────────────────────────┐
│                         │
│ ‹ Main card · [1/n]     │ ›   ← swipe the card horizontally
│   Flight · $920         │       to replace with next alternative
│                         │
└─────────────────────────┘
  • ○ ○                         ← dot indicator (how many alternatives total)
```

### Rules for the swipe-deck

- **The main card itself is the deck.** Each slot in the itinerary is one card that pages through its alternatives. The visual shape, position, and surrounding cards **do not change** on swipe — only the content of this one card swaps.
- **Gesture:** horizontal swipe (pan, not velocity-gated — user can drag finger across). Snap-back if not past threshold. Elastic resistance at edges (first / last alternative).
- **Haptic:** `Haptics.selectionAsync()` on commit to a new alternative (exactly when the card snaps to the new option), not on every pixel of drag.
- **Indicator:** a small dot row beneath the card (`•` current, `○` others) OR a counter badge `[2/5]` at the top-right. Pick one, commit to it across all cards.
- **Count:** **however many the AI returns — no hardcoded cap.** Could be 2, could be 10. UI must handle variable length. "As many best similar options as exist."
- **Remove action:** the × button lives on the card (top-right). Pressing × removes the entire slot (not just the current alternative) — and triggers timeline reflow (§4).
- **What "alternative" means:** same card type (a flight alternative is always another flight, a hotel alternative is always another hotel), same time slot (or near it — a hotel alt for Apr 6 is another Apr 6 hotel), same general constraints, varying by provider / price / class / exact time.

### Implementation notes for `TravelCardView`

The component currently lives at [`artifacts/mobile/components/TravelCardView.tsx`](../artifacts/mobile/components/TravelCardView.tsx) and has two-layer structure (main card + `AlternativeChip` row). The refactor:

1. **Remove** the `altSection`, `AlternativeChip` component, `altList`, `altHeader`, and associated styles (lines ~207-232 and corresponding StyleSheet entries).
2. **Wrap** the main card in a horizontally pan-gesture-enabled wrapper. Use `react-native-reanimated` + `react-native-gesture-handler`'s `Gesture.Pan()` + `Animated.View`.
3. **State:** replace `selectedAltId` with `currentIndex: number`. `allOptions` array stays (`[card, ...card.alternatives]`).
4. **Rendering:** show `allOptions[currentIndex]` as the card content.
5. **Animation:** as user pans, animate the card's `translateX`. On release:
   - Past threshold in either direction → commit (increment/decrement `currentIndex`, reset `translateX` to 0, fire `Haptics.selectionAsync()`, call `onSelectAlternative(allOptions[newIndex])`).
   - Not past threshold → snap back to `translateX: 0`.
6. **Edges:** at first index, block swiping right (or show elastic bounce). At last index, block swiping left.
7. **Indicator:** render a `HStack` of dots below the card, one per `allOptions[i]`, filled circle for current index.

The prop contract stays the same — `TravelCardView` still takes `card`, `onRemove`, `onSelectAlternative`, `compact`. Only the internal rendering + interaction changes.

## 4. Timeline auto-reflow — the cascade

When any card is **changed** (via swipe to alternative) or **removed** (via ×), every card below it in chronological order must readjust.

### What "readjust" means

The engine holds an ordered list of cards, each with `startTime` and optional `endTime`. When a change happens:

1. **Re-solve dependent time slots.** Any card that references the changed card's time (e.g. airport transfer → outbound flight) updates its own time.
2. **Shift subsequent cards.** If the change caused a time collision or gap, subsequent cards shift earlier or later to maintain continuity.
3. **Drop impossible cards.** If a card can no longer fit (e.g. visa card but processing time exceeds trip start date after change), flag it visually and prompt the user.
4. **Re-sort.** After reflow, the pass's cards list is re-sorted by `startTime` ascending.

### Dependency graph (what depends on what)

| Card | Depends on |
|---|---|
| Visa | Start date (must process before) |
| Insurance | Start date, end date (covers window) |
| Outbound flight | Start date |
| Arrival transfer | Outbound flight arrival time + airport |
| First hotel | Arrival transfer end time (check-in ≥ transfer arrival) |
| Activities | Hotel location, current day of trip |
| Dining | Activities (should not collide with a day activity), hotel location |
| Events | Specific event time (fixed), reflow around it |
| Inter-city transport | Between consecutive destinations' hotel check-out / next hotel check-in |
| Subsequent hotels | Previous inter-city transport arrival |
| Departure transfer | Return flight departure time + airport |
| Return flight | End date |
| Last hotel | Check-out = departure transfer start |

### Example cascades

**Example 1 — swipe flight to later departure:**
- Outbound flight changes from 10:00 → 14:00 departure; arrival shifts from 18:00 → 22:00.
- Arrival transfer moves to 22:15.
- Hotel check-in time stamp updates to 23:00 (late check-in flag added).
- First-day morning activity (if any) — drop, since the traveler doesn't arrive until night. User is notified.

**Example 2 — remove outbound flight:**
- Arrival transfer card becomes orphaned → auto-removed.
- Hotel first-night check-in becomes undefined → pass marked "incomplete," user prompted to add a flight or confirm.

**Example 3 — swipe activity to a different time:**
- Only the dining card scheduled around it moves to the new adjacent slot.
- No cards before the activity are affected.

### Conflict detection

- No two cards may occupy overlapping time. If a swipe causes overlap, the engine rejects the swap and shows a toast ("This flight arrives too late for your hotel check-in") — user picks a different alternative.
- Visa processing must complete ≥ trip start date. If the swipe moves the start date earlier than visa processing window, visa card flags red.

### Where the logic lives

- **Pure function** in a new file `artifacts/mobile/context/plannerEngine.ts`:
  ```ts
  export function reflowCards(cards: TravelCard[], changedCardId: string): TravelCard[]
  export function removeCardAndReflow(cards: TravelCard[], cardId: string): TravelCard[]
  export function detectConflicts(cards: TravelCard[]): Conflict[]
  ```
- `PlannerContext.updateCard` and `PlannerContext.removeCard` call these after any mutation.
- The engine is pure TS — unit-testable without RN deps.

## 5. Book All → Travel Pass

This part mostly works today; the spec just clarifies behavior.

1. After the user has swiped / removed to their liking, they tap **"Confirm & Create Travel Pass"** on the planner result screen.
2. `PlannerContext.bookAll(activePlan.id)` is called.
3. The `activePlan` is **compiled** into a final Travel Pass:
   - `status: "upcoming"`.
   - `isPublic: false` (user opts in to share separately).
   - `travelBuddyRequests: 0`.
   - `totalCost`: sum of all card `price` fields.
   - `coverImage`: auto-selected based on destination (TBD — for now, use a deterministic color from the title).
4. Inserted into `passes[]` state and persisted to `AsyncStorage.travelbook_passes`.
5. `activePlan` cleared.
6. User is navigated to the **Passes tab** — which is the source of truth from then on.
7. In Phase 6 (backend): `bookAll` also fires provider bookings, captures payment, sends confirmation emails.

## 7. Implementation order

When we build this, sequence matters:

1. **`plannerEngine.ts`** — pure reflow logic first. Unit-testable. This is the brain.
2. **`PlannerContext`** — expand `generateItinerary` to emit all 12 card slots. Add reflow calls to `updateCard` / `removeCard`.
3. **Planner form** — add Purpose pill + free-text field. Extend `PlannerPreferences`.
4. **`TravelCardView` refactor** — remove alt-chips, add swipe-deck gesture. Haptics. Indicators.
5. **Planner result screen** — no change needed, it already renders `TravelCardView` per card. Will "just work" once the card internals change.
6. **Book All → Pass** — audit the existing flow, add `coverImage` fallback, verify reflow result is what gets booked.
7. **Phase 6 only**: swap the fake `await new Promise` for a real LLM call.
